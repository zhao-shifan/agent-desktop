【一句话总结底层】
智能体 = 大模型（规划器） + 程序代码（执行器/调度器） + 循环
大模型只输出文本，不会自己干活；代码负责：给它看工具清单 →
解析它想调哪个工具 → 执行工具 → 把结果回灌 → 循环直到完成。

标准循环（伪代码，所有 agent 的核心就这 30 行）：
    msgs = [system提示词, 历史对话, 用户问题]
    for step in range(MAX_STEPS):          ← 步数预算，防死循环
        resp = llm(msgs, tools=工具清单)   ← 模型决策
        if 没有 tool_calls: 结束，返回 resp.content
        msgs.append(resp)                  ← 意图必须原样回传
        for call in resp.tool_calls:
            result = 执行工具(call)        ← 真正干活的地方
            msgs.append(tool_result(call.id, result))
注意：用原生 function calling（API 的 tool_calls 字段），
不要用 2023 年那套"让模型输出 JSON 文本再解析"，已经淘汰。

一、必配模块清单（12 块，缺前 8 个不算完整智能体）
================================================================

 1. LLM 适配层
    - 统一接口封装：Ollama / DeepSeek / 智谱 / OpenRouter 兼容
    - 换模型只改这一层，上层循环不动
    - 重试：429/5xx 指数退避（3s→6s→12s，最多2次）

 2. 系统提示词（System Prompt）
    - 角色定义 + 规则 + 工具纪律（能不调工具就不调）
    - 工具使用纪律示例："涉及实时信息才调用；常识/写作直接答"

 3. 工具注册表（Tool Registry）
    - {工具名: 函数 + JSON Schema 描述}
    - 描述写"什么时候用"，比"怎么用"更重要（模型靠它选工具）

 4. 工具执行器
    - 解析参数 → 权限检查 → 执行 → 返回字符串
    - 单个工具失败返回错误文本（不中断循环，让模型自己纠正）
    - 输出截断（如 12000 字符），别把超大文本灌回模型
    - 多个 tool_calls 用线程池并发执行

 5. 步数预算（max_steps / MAX_ROUNDS）
    - 必须有，防止无限循环烧 token
    - 超限时不要硬编码一句"失败了"，而是追加一条消息
      "不能再调工具，基于已有信息立即总结"再调一次模型

 6. 终止判断
    - 模型返回不带 tool_calls 的纯文本 = 结束

 7. 上下文管理
    - 超阈值（如窗口的 85%）时把较早历史摘要压缩成检查点
    - 近期 25% 左右逐字保留（引用"上面/刚才"才准）
    - 上下文溢出报错 → 压缩后重试一次

 8. 会话持久化
    - 前端 localStorage 或服务端 SQLite
    - 多轮历史、分支对话

 9. 前端进度展示
    - 工具执行状态行（工具名+参数+完成✓）
    - 思考心跳（模型 6 秒没响应就显示"思考中 Xs"）
    - 步骤号/耗时/token 用量（进阶）

10. 工具集（写改搜读，参考 SWE-agent 的 ACI 理论）
    - T0 必备：read_file / write_file / edit_file / grep /
      glob / list_dir / run_command / web_search / web_fetch
    - T0.5 通用标配（2026-11-23 已加，均有出处）：
      get_time       ← LangChain datetime 工具同用途
      calculator     ← LangChain Calculator 同用途
                      （AST 白名单求值，不用 exec）
      run_python     ← smolagents PythonInterpreterTool
      wikipedia_search ← smolagents WikipediaSearchTool
                      （MediaWiki API 免 Key）
      save_note / search_notes ← mem0 记忆层同用途
                      （RAG-lite：JSON + 关键词打分）
    - 关键：读写要对称！只有读没有写 = 残废 agent
    - edit_file 设计要点：old_string 必须唯一命中，多处拒绝
    - 权限分级：路径白名单 > 命令开关（run_command 和
      run_python 都要受 allowCommand 控制）> 危险命令黑名单
    - 不要用 RestrictedPython 当沙箱（不安全），自用
      白名单+黑名单就够

11. 复盘/追踪（trace）
    - 每轮 msgs 落 JSONL 文件，出问题能定位到具体轮次
    - 高星项目都叫 replay，自用 JSONL 够了

12. 长期记忆（可选，进阶）
    - SQLite + BM25 关键词检索即可，不必上向量库
    - 真要做 RAG 再考虑 sqlite-vec（单文件、免费）

二、LangChain 要不要？
================================================================

不要。理由：
- 原生 function calling 已把"模型接工具"这件事标准化，
  框架最大价值消失
- 框架抽象遮住 prompt，调试 agent 90% 时间在看发了什么
- 学习成本 > 它省下的胶水代码

什么时候才考虑框架（全部免费开源）：
- LangGraph(MIT)：要断点续跑/人工审批插中间/状态图
- OpenAI Agents SDK(MIT)：要 handoff/护栏/内建 tracing
- smolagents(Apache-2.0)：想试"模型写代码调工具"范式
- CrewAI(MIT)：多角色流水线
注意：n8n 不是免费软件（Sustainable Use License），商用避开。

判断口诀：
  能提前画出流程图的 = workflow，写普通代码，别用框架
  模型在运行时自己决定下一步的 = agent，才需要循环/框架

五、避坑清单（本人踩过/教程里的坑）
================================================================

1. 别用"模型输出JSON文本再解析"的旧 ReAct 写法，
   直接用 API 原生 tool_calls
2. 别信 RestrictedPython 沙箱，防君子不防小人
3. 别一上来装 ChromaDB 向量库，SQLite+BM25 够用
4. 别用 Streamlit/Gradio 替代自研前端（倒退）
5. Ollama 小模型（4B级）工具调用经常出错，云端免费API为主
6. base64 编码大文件要分块，String.fromCharCode(...大数组)
   会爆栈
7. Service Worker 缓存会让人改了代码"没生效"——每次改版
   必须升缓存版本号
8. 免费API有速率限制：必须做指数退避重试
9. 工具输出必须截断再回灌，否则上下文爆炸
10. 打包 exe 注意：PyInstaller 单文件要放纯英文路径
